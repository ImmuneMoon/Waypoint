# Waypoint — working in this repository

Waypoint is an Electron virtual tabletop: a GM's campaign (maps, tokens, handbook pages, character sheets, sound, music, fog,
dice) hosted from one machine, with players joining peer-to-peer. This file is the build, test and house-rules reference for
anyone (or any tool) changing the code. The README covers installing and using the app.

## Layout

- `system/app/` — the application. `index.html`, `style.css`, and `scripts/*.js` as ES modules. `index.html` holds no script of its own: four
  classic scripts sit at fixed places in its head — `boottheme.js` (before the stylesheet), `booterror.js` (after it, before everything
  else), `bootprefs.js` (directly after `/api/prefs.js`, before the first module: the launch merge of the settings file) and
  `bootdiagram.js` (last, after the libraries: the diagram config). Modules talk through
  `window.wp*` globals (`wpNet`, `wpSheets`, `wpSystemCore`, `wpDocRender`, `wpVtt`, …) and the shared `state.appState`.
  `scripts/gencore.js` (`wpGenCore`, pure, importing `fogcore.js` and `buildcore.js`) is the dungeon generator's pure half: one seed and five settings make one dungeon, the same every time (`cleanGen`, `genDungeon`, `dungeonPieces`). `scripts/charlist.js` (`wpCharList`) draws the left panel's Characters section from the campaign's sheets. Its rows wear a class of their own (`ch-row`), never the tree's `sidebar-item`: sidebar.js binds the tree's click, right-click, double-click and drag to the rows of its own three lists, and a new section of the panel keeps its rows out of them. What a joined player's panel holds is judged in ONE place, sidebar.js `panelJudge(chN)` (`panelBare`, `panelHeld`: the whole panel steps aside with no page and no character, the Handbook section and its rail icon alone with a character and no page): the section's `sync` asks it wherever it knows the count, since a character that arrives reaches only `render()`, and nothing else writes the class `no-handbook`. What a row does is the sheet module's to do and to judge, and nothing of a sheet is asked of it on someone else's table whose link is down (`away`), since sheets.js would read that screen as the GM's own. `scripts/textfmt.js` (`wpTextFmt`) is the pure core for the look of one plain text field, stored beside the text and never inside it
  (`{ size?, color?, b?, i?, u?, st?, link?, spans: [{ s, e, color?, b?, i?, u?, st?, size?, link? }] }` — `st` is strike, `s` a span's start; a size or a link is the field's own only when every character has that one: `cleanFmt`, `cleanLink`, `runsOf`, `respan`, `apply`, `clear`, `stateAt`); `docrender.js`
  imports it and `safecore.js` (both pure leaves). `textfmt.js` also holds `linkParts` (the web addresses in a plain text) and `typedLink` (what a
  typed address becomes), both ending in `cleanLink`. `scripts/lookcore.js` (`wpLook`, pure, importing `textfmt.js` alone) is the look of a text OUTSIDE a planner (item 35: a sheet's text, a Journal note of your own, the notepad): a record `{ fmt?, font?, sig }` whose `sig` is the signature of the very text it was made for (`textSig`), cleaned by a RULE of the place (`RULES`: LINE, NOTES, NOTE, PAD; `fieldLook`, `cleanRec`, `makeRec`). The signature guards against ACCIDENT (a look laid over a text it was not made for), never against intent: anyone can sign any text. So a place keeps a look only where whoever may write the text may write its look, and a rule is named by the code of the place, never read from data. Half a character with no other half signs as the replacement character, which is what the table's connection carries in its place (it packs text as UTF-8), so both ends sign alike. One address over touching parts of several looks is ONE link: counted once against the bounds (`LINKS`, `LINK_CHARS`), kept whole or dropped whole. `lookWeight` weighs a cleaned record only, and for one it is never less than the characters JSON gives the record (its fixed parts as the worst JSON writes them, and each string as JSON writes it: an address the link rule kept may hold a quote, a backslash or half a character), so a budget counted in it bounds what is sent and saved. A CHARACTER keeps the looks of its text and notes values as `looks: { fieldId: record }` beside `values` (systemcore.js `lookRule`, `cleanLooks`: only for a text or notes field of the system, only a record that is that very text's, in the order of the system's fields; no size on a one-line text, never a font on a sheet). `cleanChar` cleans them on every way in (a load, an import, a snapshot, a host's copy), `charView` puts them on the OWNER's whole copy alone (a teammate's hover copy holds none), and a text changed by any writer that knows no looks leaves a look every reader drops. A look lives while its text stands: once the host's text of a field is another, the look made for the old words is gone for good, on the machine that owns the campaign (sheets.js `lookPrune`, asked through `typeof` from `afterCharChange` and `charChanged`, the two funnels every change of a character ends in, before the save) and in what a player's app remembers as the host's word (net.js `styleLay`), so the old words typed again find no look on one machine and not on another. A new funnel for a character's change asks `lookPrune` too. A look is set only through `applyStyle` (the right is the right to edit the text as it is stored, asked before the record is read) and travels in messages of its own, so the edit path is as it was: a player's `char-style`, the host's `charstyle-ack` / `charstyle-deny`, and the host's word `charStyle` to each connection that holds the character whole (net.js `[netcheck:charlook]`, `[netcheck:charstyle]`, `[netcheck:charstylein]`; sheets.js `commitLook` is the one place a sheet sets one). The host's branch has char-edit's gates in char-edit's order and a limiter of its own, and what it tells a connection is the look that connection's OWN copy holds (`net.syncCharStyle`), never a record as handed in. A player's app keeps looks only on its OWN WHOLE copy and does not take a host's word for it: a look a host lays on a teammate's hover copy, or on a whole copy that is someone else's, is taken off as the copy comes in (`styleOurs`, `noteHostChar`, asked through `typeof` from the three places a host's copy arrives: the snapshot, `chars`, `char`). A new reader of a character's looks on a player's app reads them from such a copy alone. A player's app holds what the host last said (`_charHostLook`), lays the looks still waiting for an answer over it (`styleLay`, run from `reapplyPending` whenever the host's copy or a waiting change moves), and cleans a host's record again against the text the host last said the field holds. A host that knows text looks SAYS SO in its join snapshot (`looks: true`, read as true only: `styleHostKnows`), so an older Waypoint is known and never guessed from a silence: a player's app sends no look to a host that did not say it, lays and waits for none, and says at once that the GM's Waypoint is older (`net.charStyle`; a place that offers styling asks `net.looksOk()` first). At a host that did, a look that goes unanswered is said as any unanswered change is. A later capability of the wire that an older host would answer with silence is announced the same way, by a true-only key of the snapshot. The three char-edit branches and `net.syncCharDelta` are not touched by any of this. A SHEET draws a text or notes field with its look where the field is only READ in that view (a locked sheet, the HUD, a window of its own, a field that is not the viewer's to change): sheets.js `lookNode` for a field and `lookInto` for a one-line text in the sheet's header, both through the reader with `ask: true` (a link on a sheet asks first, whoever wrote the words) and the look read through systemcore `lookOf` (the cleaned record for the very text stored, or none). Both are asked through `typeof`, from `fieldNodeBody` before the two lines it always had for a text and for notes, and from `headerBlocks` after the value's span is made: with no look, or no reader, the field is drawn exactly as it was. A new place that shows a character's text value asks `lookOf` and draws through the reader, never from `c.looks` itself. Such a text is drawn where it is READ only through linkgate.js `fillRuns` (`window.wpTextRead.fill(el, text, rec, document, { rule, typed, ask })`, for a module that may not name linkgate.js): the record through `cleanRec` by the rule of the place, a span a run with a strict colour, fixed words and a size step, a run's link as one `<a>` with href, target and rel, the element's font SET OR CLEARED at every draw, elements and text nodes only. With `typed`, the web addresses typed in the text are links too, and only where the rule of the place takes links (`wpLook.ruleLinks`): they are found ONCE over the whole text, as `fillLinked` finds them in the plain text, never part by part, so every piece of a typed address leads to the WHOLE address whatever looks lie over it, and one that reaches into a part with a link of its own is not linked at all. A new reader of typed addresses does the same: a boundary between two looks inside an address must never make a link to a cut address, which is another place. `scripts/linkgate.js` is the one place a click on a link is decided (a capture listener
  on the document for click, auxclick and a drag's start, in every window): `linkVerdict` the pure rule, `fillLinked` the renderer that draws a
  plain text's web addresses as links.
  `scripts/buildcore.js` (`wpBuildCore`, pure, importing `fogcore.js` and `safecore.js`) is the map builder's pure half: the code-drawn textures, the materials and the lattice maths.
  `assets/` holds the bundled presets, sounds and the tutorial campaign's art; `assets/fonts/` and `assets/icons/` hold a fixed, licensed list
  (Inter, Font Awesome Free — licence texts beside them): a new glyph needs its file, a `GLYPHS` entry in systemcore.js, its attribution
  comment and the bundled-files test. `assets/fonts/` also holds 22 typefaces for text (the owner's yes of 2026-10-08, by name): each a folder with
  ONE TrueType file as its makers published it (never changed, subset or converted: several reserve their font name) and its `OFL.txt`,
  listed with its copyright notice in `assets/fonts/FONTS.txt`. `textfmt.js` `FONTS` names the families, `style.css` has one `@font-face`
  rule a file, and systemcheck holds each file to its length and SHA-256. A new typeface needs the owner's yes with its file, source and
  size named, then its folder, its `FONTS` entry, its rule, its `FONTS.txt` entry, the credits (About, the README) and its pin. `assets/vendor/` holds the three bundled libraries (PeerJS 1.5.2, Mermaid on the 10 line, html2canvas
  1.4.1; MIT, each licence text beside its file, bytes kept by `.gitattributes`): replacing one means the new file, its SHA-256 and version
  in sinkcheck's `LIBS`, and its licence header; Mermaid stays on 10.x. `version.json` is written at build time.
- `system/resources/app/` — the Electron shell: `main.js` (a small local HTTP server that serves `system/app` and a handful of
  JSON endpoints over the saves folder, loopback only, own-origin only), `updater.js` (checks, applies and undoes a signed update, and fetches, checks and starts the installer for one that changes the core), `updatekey.js` (the public half of the update signing key, written only by `tools/signkey.js`), `libstore.js` (a campaign's library pack files beside the save, shared with the dev server), `reqguard.js` (what the local server takes and refuses — the launch secret, names, an upload's kind and size, bodies, deletes, backups — shared with the dev server), `shellguard.js` (the rules for the shell's windows as plain functions: which windows a page may open, which links reach the system browser, permissions, Developer mode, the loopback listen; and the page's script policy — `pagePolicy`, `pageHeaders`, `savesType` — which both servers send with every page), `package.json` (the app version and the recorded Electron version).
- `tools/` — `dev-server.js` (run from source in a browser), `release.js` (build), `signkey.js` (makes and checks the update signing key), `shellrev.js` + `shellrev.json` (the core's recorded revision), `electronstub.js` (a recording stand-in for the electron module that runs the real main.js under plain Node for servercheck; it never starts Electron), `boxdom.js` (a page of plain objects for the planner editor's boxes — elements, events, one focus and one selection, and an engine that edits a box as a browser does; it refuses innerHTML; required by textcheck and sinkcheck, not a suite), and the offline test suites `*check.js`.
- `saves/`, `dev-saves/`, `dist/`, `docs/*.md`, `.claude/` are git-ignored: a table's data, scratch data, build output, local
  planning notes and machine-specific launch configs never enter the repository.
- `CAMPAIGN_INTEGRATION.md` documents the save-file schema for tooling that generates content.

## Running from source

```bash
node tools/dev-server.js [savesDir] [port]
```

Defaults: `./dev-saves` and port 3999. The shell's server answers only requests that carry that launch's secret (its own windows send it); the
dev server runs without one unless `WAYPOINT_LAUNCH_SECRET` (32 characters or more) sets it. The dev server holds both loopback addresses of
its port and exits 1 when either is taken; its Update and Restore answer 409 unless `WAYPOINT_SYSTEM_DIR` names a scratch copy of `system/`. The dev server mirrors the shell's HTTP API, so the front end runs unchanged in an
ordinary browser. **Never point it at a real saves folder** — use a scratch folder per instance.

Multiplayer is verified with two instances on different ports and different saves folders (a GM at one, a player at the
other), joined through the real Host / Join screens. `.claude/launch.json` (local, ignored) names such a pair
(`waypoint-gm`, `waypoint-player`) for the Claude Code browser pane; recreate it on a new machine with scratch paths.

An installed Waypoint (`Programs\Waypoint`) is never touched from here: changes reach users through releases only.

## Editing rules

- **Line endings are per file and per checkout.** `.gitattributes` normalises the index to LF; the working tree follows
  `core.autocrlf`, so on a Windows checkout with `autocrlf=true` a file comes out CRLF whenever git writes it (a checkout, a
  merge), while one git has not rewritten keeps what it had. Never trust a list: check `git ls-files --eol <file>` before
  editing and keep what you find (a patch script detects the EOL per file; a test normalises CRLF before a regex that expects a
  newline). `popout.js` and `docpanel.js` are binary to git (`docpanel.js` holds three NUL bytes, its signature separators, and is LF-only; textcheck pins it): edit them byte-exact or not at all. EOL
  churn never shows in `git diff`, so it is easy to break silently.
- Prefer a small Node patch script that does **exact-match, all-or-nothing, EOL-preserving** replacements over ad-hoc shell
  edits when a file needs several changes. Never build string literals through shell escaping (backslashes get lost);
  never append a `//` comment to a one-line handler (it comments out the tail). `node --check` on a `.mjs` copy pinpoints a
  syntax error that parsecheck attributes to every importer.
- Opt-in configuration renders exactly as before when absent (a system without a band, a page without a look, a section
  without colors is byte-for-byte unchanged). Keep default shapes stable — suites assert them.
- **Wire and file safety:** nothing from the wire, a save file, an import or another origin reaches `innerHTML`, an
  attribute, a URL or a disk path without a tested sanitiser; a client re-validates what a host sends; GM-only data

  what another step (or the user, in Try it yourself) left open, sparing only what `stageFor` says the step's target needs — a step that opens
  something new gets its case there (tutorialcheck fails otherwise). While a card is up the page takes no press but the card's; a new control
  of the tour goes in the card or the chip, never on the page. The tour's keys are judged in `tourKey`: a question or a prompt of the app's own that is up takes every key (`appAsking`), Enter on a button of the card's own is that button's press (`tourButton`), and Enter on a button of the page still moves the tour, so that nothing under the card is pressed. The card is drawn again at every step, so `show` puts the focus back on the button it was on, by its id (`cardFocusOf`, `cardRefocus`): a second Enter on Back goes back again. The naming prompt the tour owes a fresh save is never raised while someone else's table is on screen, and New Campaign refuses there itself.
- **Nothing is written into the page as script:** no inline `<script>`, no `on…=` attribute in `index.html` or in markup a script builds (wire
  handlers with `addEventListener`), no `eval` / `new Function` outside `devconsole.js`. Both servers send a script policy with every page
  (`shellguard.pagePolicy`, a response header, never a `<meta>`: Developer mode adds text run as code and nothing else), which would
  silently stop them, and sinkcheck fails. A new outside address (a signalling server of the app's own, a web picture) is added to
  `pagePolicy` first; the policy travels with the core. No script of the app names the bundled libraries' folder, comments included (say
  "bundled": sinkcheck scans every script).
- **A change under `system/resources/app/` or to `installer.iss` is a change to the core.** Run `node tools/shellrev.js` afterwards and
  commit `tools/shellrev.json` (updatercheck fails until you do), and raise the version in `package.json` BEFORE the first core edit of a
  new release: `since` is the version the tree said when the hash moved, and it becomes every later release's `minShell`. `SHELL_WANTED`
  in settings.js must name the same version. Never start the Electron shell and never run a compiled installer from an agent session
  (the installer ends every running Waypoint and overwrites the installed copy): shell code is verified by reading and by plain Node.
- Put a design choice to the maintainer as a short multi-choice question with the recommended option first, then build.

## Git, versions and releases

- Commit locally with a message in the house style: `<version>: <area> — <what changed and why>`, body in prose.
- **Push `main` after a verified fold** (all suites green, live check done); CI runs on the push. **Never publish**: no
  GitHub Release, no tag, no `node tools/release.js --publish` — the maintainer publishes when a release is ready.
- Published numbers are frozen. Before folding a change in, run the release guard: compare the GitHub `/releases/latest`
  tag with `system/resources/app/package.json` (and `git fetch --tags`). If the package version is already published, the
  change takes the next number; otherwise it folds into the open one. Patches run to `.9` before a minor bump. `TUTORIAL_VERSION` in tutorial.js is raised to
  package.json's version when `STEPS` or the demo campaign change, and is never ahead of it (tutorialcheck fails, and with it the release
  build): a branch cut while a later number was open takes the open number at the fold.
- `node tools/release.js` writes `system/app/version.json` and the README's release line from `package.json`, zips the
  app with a `.sha256`, and compiles the installer (Inno Setup 6) into `dist/<version>/`. Release notes go in
  `WHATSNEW.txt` and `system/app/assets/whatsnew.txt`.
- **Releases are signed.** `tools/release.js` builds only with the update signing key at hand (`WAYPOINT_SIGNING_KEY` names the private
  key file, kept outside the repository; `node tools/signkey.js --check <path>` says whether a file is the right one) and only while
  `tools/shellrev.json` is fresh. It writes `waypoint-app-<version>.zip.sig` and `Waypoint_Setup.exe.sig` beside the other assets (each
  over the file's name, its SHA-256 and the version) and publishes `minShell` from the record, in the manifest and inside the zip's own
  version.json. An install takes an update only when it checks against the public key its shell carries. The private key is never
  committed, copied into the tree or printed; `*.pem` is git-ignored and left out of the installer.
